# Solarnet glossary

Runtime, task, and history terms. Language, type, and Canon terms are in the
[Pets glossary](../pets/docs/glossary.md).

- **action (game flow):** A Player's accepted corporation play, Prelude play, action-phase choice, or final greenery placement. An action includes its resulting work, even when another Player must respond. Passing starts no action. A turn can contain several actions. This is distinct from an authored red-arrow [action](../pets/docs/glossary.md) such as a card ability, whose use can occur within the game-flow action already in progress.
- **action offer:** A pending opportunity supplied by the game's rules to start a game-flow action or pass. It is distinct from an offered option, which is an answer currently presented by a client. The `OfferAction` signal can produce an action offer or request a baton transition without presenting a choice.
- **ActorAccess:** The passive, permissions-aware conduit through which an agent invokes engine mutations for its Actor. Callers do not bypass the Actor's unique agent to use it.
- **Actor:** The in-game identity to which a task is assigned or a change event is attributed. Players and Admin are Actors; a client is software that calls an Actor's Agent. See the [Pets definition](../pets/docs/glossary.md).
- **agent:** The Actor's route for client requests and authorization in one configured game world. It retains the right to be consulted for that Actor's choices unless it has installed a matching standing policy that lets the engine handle a covered task. It is not a task queue or core-engine concept.
- **assignee:** The Actor whose Agent controls authority to select, narrow, or execute a task, including any standing policy it installed for that task. An instruction-side `BY` can change the assignee before execution.
- **automatic advancement:** An agent applying an authorized answer and moving past a decision when no meaningful choice remains, possibly after pruning or collapsing. Advancement is distinct from the engine executing a task. It does not authorize choosing among meaningfully different outcomes. Whether Player agents need this service remains open; Admin's mandatory handling is separate.
- **baton handoff:** Transfer of the `Baton` from the Player whose turn is ending to the next Player. A task handoff can occur during a Player's turn without a baton handoff.
- **baton removal:** Removal of the `Baton` when a turn-based phase ends without passing it to another Player in that phase.
- **bootstrap:** The shortest special prefix needed to construct a game world and establish Admin as an ordinary Actor. Once Admin can carry out assigned tasks through the normal lifecycle, bootstrap is over; later game setup remains ordinary Admin work.
- **cause:** Attribution attached to a task and copied to its resulting change events. For effect-generated work it pairs the type of the context Component whose effect fired with the ordinal of the triggering change event. Those pointers explain the causal chain but do not uniquely identify which of several matching effects fired, so a cause is attribution rather than a complete derivation proof.
- **change event:** A game event recording one state change together with its ordinal, Actor, and optional cause. Task lifecycle changes are recorded separately as task events.
- **choice:** The option selected for a decision by the client or an authorized policy. A choice can be retained in a draft before any game-world change.
- **clearance:** The point at which a game-flow action and its consequences have finished, including other Players' responses, removal of its `ActionScope`, and resulting cleanup. The game has advanced to the next independent offer or phase, or has ended; accepting that next offer is a different action. An empty task queue for the initiating Player does not by itself establish clearance.
- **closed task:** A task whose immediate instruction needs neither further evaluation against the current game world nor further elective narrowing. An instruction that carries work inside braces or as quoted content can be closed regardless of what that carried work will need when it is handled. This includes `EACH` fanout and `NOW`, `SOON`, `LATER`, or `FINALLY` dispatch. Closure does not mean the task has executed or that execution will succeed. Antonym: open task.
- **closed instruction:** See the [Pets definition](../pets/docs/glossary.md). Its immediate work needs neither evaluation nor elective narrowing.
- **collapse:** Represent options or routes proved to have equivalent gameplay outcomes by a representative, preserving every distinct reachable end-of-action state and later meaningful choice. A useful case is proving a task safe to complete early, so its other orders need no separate analysis. Event order and cause history alone do not make outcomes different. Distinct from pruning a nonviable option.
- **component graph:** The logical directed graph whose vertices are Components and whose edges are dependencies. Because a type includes the exact types of its dependency targets, the game world stores the vertices as a multiset of types rather than as separately identified objects and edges.
- **client:** The program making requests through an Actor's Agent, such as a UI, script, or test. A client can submit choices for different Players through their separate Agents; the Player remains the in-game decision maker.
- **decision:** An Actor-owned question whose possible answers are options. Choosing which eligible task to handle next is a decision; an open task can present further decisions about an alternative, target, amount, or card identity.
- **decision graph:** The Agent's possible sequences of decisions, submitted tasks, and resulting game states from a current choice through the relevant endpoint. For a game-flow action, that endpoint is clearance.
- **dependent removal:** Automatic removal of Components that depend on a Component being removed, performed first and cascading as necessary.
- **direct driver:** The planned test adapter that exercises the interaction API directly, following the same interaction script as a UI driver.
- **drain:** To become empty. Once no ordinary task remains, the earliest remaining deferred work (`LATER`, then `FINALLY`) becomes ordinary.
- **elective narrowing:** A client or authorized policy supplying a permitted choice that makes part of an open task's instruction more specific. Evaluation may follow and expose further decisions.
- **engine:** The passive mechanism that validates Actor-attributed mutations and calculates their state consequences. It is not an Actor or Component.
- **engine transaction:** A command attributed to an Actor, including its task edits, component changes, required parts, immediate effects, invariant checks, and admission of resulting tasks. An Agent call can perform several engine transactions.
- **evaluation (task):** Engine interpretation of a task's instruction against the current game world without executing it. This includes checking gates, computing metrics and amounts, and applying forced deductions. Evaluation and elective narrowing may alternate before a task closes. Type-system resolution of an Expression to a Type retains its separate name.
- **execution:** Applying a closed task instruction to the game world, including any resulting task or component changes. Execution can admit further pending work and need not clear the enclosing action.
- **event log:** The ordered history of state changes and task lifecycle events in a game world. It supports recording, inspection, and restoration; it is not part of the current game state.
- **ex machina:** A change to game state outside ordinary handling of pending tasks, including their selection, narrowing, and execution. Direct task admission or removal and exact corrections are examples. `Agent.exMachina` is the correction facility with its own validation and effect rules. Replaying or seeking recorded history restores a state rather than submitting a new game change.
- **follow mode:** The mode in which Solarnet calculates the state transitions for a game played elsewhere and trusts client-supplied draws, reveals, discards, and plays.
- **game state:** The current component graph and task queue under a fixed premise. Selected and deferred tasks remain part of the state. Event history and timeline position are not additional gameplay facts. For decision-graph comparison, task ids and cause-event ordinals alone do not distinguish otherwise equivalent states.
- **game world:** The complete runtime container for a game: its current game state, event log, timeline, and class table, together with the catalog and immutable premise behind them. ActorAccess and agents are configured above it.
- **interaction API:** The planned Platonic UI: calls for inspecting information, navigating views, answering decisions, and undoing, expressed without depending on pixels or a particular widget layout. A direct driver and a UI driver can run the same interaction script through different surfaces.
- **live effect:** A component effect paired with its existing context Component, so that it can respond to change events. It counts according to the multiplicity of that type.
- **needs narrowing:** See the [Pets definition](../pets/docs/glossary.md). This check does not say whether the instruction also needs state evaluation.
- **offered option:** An option currently presented to the client as an answer to a decision. Whether an option has been offered is separate from what has been proved about its viability.
- **open task:** A task whose immediate instruction still needs evaluation against the current game world, elective narrowing, or both before it closes. These activities may alternate. Antonym: closed task.
- **open instruction:** See the [Pets definition](../pets/docs/glossary.md). Its immediate work still needs evaluation, elective narrowing, or both.
- **option:** A possible answer to a decision, whether proved viable, proved nonviable, unknown after analysis, or not yet examined. An unexamined option remains an option even if it is not in the active offered set.
- **pending task:** Any task still in the task queue, including selected and deferred tasks. Its assignee's Agent has the applicable authority to handle it when priority and deferral rules permit.
- **preparation (task):** The work of bringing an open task to a closed instruction through evaluation and elective narrowing. It describes the task lifecycle, not a separate engine processing phase.
- **prune:** Remove an option from the active decision after proving it nonviable. Merely leaving an unexamined option out of an offered set is not such a proof. Distinct from collapsing equivalent options.
- **REgo PLastics:** Solarnet's command-line interface for driving the engine.
- **selected task:** The pending task chosen to finish next. Selection sets `Task.selected` and excludes competing task commands because evaluation has read the current game state. The task may remain open and accept further narrowing from its assignee.
- **settled outcome:** The resulting game state used for a decision-graph comparison after a submitted transaction and its mandatory Admin consequences have finished. Player tasks may remain pending, so a settled outcome is not necessarily action clearance. Compare component and task changes; event order, task ids, and cause-event ordinals alone do not distinguish outcomes.
- **selection:** The choice of which eligible pending task to handle next. Selection marks it selected and evaluates it; the task may remain open. Its current assignee makes the choice through that Actor's Agent.
- **state change:** An exact Component gain, removal, or transmutation that occurred in a game world.
- **standing policy:** An Actor's advance authorization for future matching tasks. It can permit execution of a closed task, such as accepting Arctic Algae plants, or supply a meaningful answer, such as choosing titanium for that Actor's Philares reward. Pruning and collapsing are Agent analysis rules, not standing policies.
- **System:** Admin-only machinery. A normalized queued task containing an elementary gain of a System Component, alone or under a top-level instruction-side `BY`, begins assigned to Admin before any Player could select it. A later explicit `BY` remains authoritative, but the gain still cannot be performed by any Actor except Admin. An unowned System occurrence does not implicitly restrict effect matching by its Actor. Presentation visibility is classified separately.
- **task:** A unit of pending work containing an instruction, current assignee, optional cause, and lifecycle metadata. It represents both what must eventually happen and the choices still permitted.
- **task handoff:** During a Player's turn, that Player releases a specific selected task for another Player to handle through their Agent. The active Player retains the baton and may resume ordering newly queued work if the action remains open. Each selected task released this way is a separate handoff; Pluto's draw and later discard are separate handoffs. A `BY` change of an existing task's assignee does not by itself constitute a task handoff.
- **task event:** An event adding, editing, or removing a task in the task queue. Task events are part of game-world history; their effects on pending tasks change game state.
- **task id:** An internal handle for a task, equal to the ordinal of its add event and stable through edits. A differing id alone does not make otherwise equivalent game states different.
- **task queue:** The one stored, unordered set of pending tasks in a game world. Every task records its assignee; Actor-specific queues are filtered views of that set. Player clients choose the order of their available tasks.
- **task result:** The retained change events and newly pending task ids returned by an Agent call or engine request.
- **task narrowing:** Replacing part of a selected task's instruction with a permitted more specific form. A client's elective narrowing can be recorded as task state without executing a component change. Evaluation may then determine more of the instruction or expose another decision.
- **triggered instruction:** The instruction produced when a live effect matches one change event.
- **turn:** The period during which a Player holds the baton. A corporation turn contains its corporation action; a Prelude turn contains that Player's Prelude actions; an action-phase turn contains zero, one, or two actions, except that the last Player still taking actions may take more; a final greenery turn contains all that Player's greenery placements. Setup discards, research, production, Supercapacitors, and global-event decisions outside these turns do not become actions merely because a Player must answer. See [Canon turns and game flow](../pets/docs/agents/GAME_FLOW.md#turns-and-turn-offers).
- **UI driver:** The planned test adapter that follows an interaction script by operating the running interface, including navigation and visible controls, instead of calling the interaction API directly.
- **viability (option):** Whether at least one continuation after choosing an option reaches the relevant endpoint without a dead end. For a game-flow action, that endpoint is clearance. Analysis can prove viability, prove nonviability, or remain unknown; an option may also be unexamined.
